## Decisions

| Area | Selected behavior | Owner follow-through |
|---|---|---|
| Private Lambda egress and cost | Use dual-stack private subnets and one egress-only Internet Gateway. Keep NAT disabled and do not add paid interface endpoints. The gateway has no hourly fee; outbound data transfer can be billed. Lambda security groups allow IPv6 TCP 443 only; existing IPv4 egress has no public IPv4 route. S3 remains on the free gateway endpoint. Four interface endpoints across two AZs would cost about $58.40/month in fixed hourly charges, before data processing. | A verified the dual-stack path from temporary private Lambdas: read-only API calls to Secrets Manager, SQS, SNS, Cognito, and SES succeeded, then a separate read-only probe retrieved the RDS-managed username/password and connected to PostgreSQL with `sslmode=verify-full`. No NAT, endpoint, or security-group changes were needed. The first probe was removed; teardown of the second is in progress after testing. |
| Upload-to-worker trigger | `POST /kyc/submit` is the only producer. Do not add an S3 event notification. Queue remains standard and has the six fields already in the worker contract. | B sends one job after committing the document and attempt. A worker remains idempotent under SQS redelivery. |
| Attempt/key lifecycle | `/kyc/upload-url` allocates and persists the attempt before upload. Its key is `documents/{customer_id}/{attempt_id}/{file_name}`. `/kyc/submit` verifies the uploaded S3 object's metadata, commits the document row, then sends SQS. | C uploads directly to the returned presigned URL and submits the same key and file name. Abandoned pre-upload attempts remain `PROCESSING`. |
| DB/SQS recovery | Do not add an outbox for the college demo. If the DB commit succeeds and SQS send fails, return an error and keep the attempt `PROCESSING`; the client retries the same submit request. Duplicate queue messages are safe because worker persistence locks by attempt. | B/C retry the same attempt and key. Do not allocate a second attempt unless the reviewer requested re-upload. |
| Repeated worker failure / DLQ | Queue max receive count is 3. On the third failed delivery, A tries to atomically set case and attempt to `REVIEW_REQUIRED` and write a `REVIEW_REQUIRED` audit event with `OCR_RETRY_LIMIT`; the record still fails the invocation so SQS retains it in the DLQ and the existing alarm fires. If RDS is unavailable, the status update can fail; the message remains available for operator investigation/redrive after recovery. | C displays `REVIEW_REQUIRED` as an actionable review state. B's reviewer APIs can use the existing review queue. Operators inspect the DLQ and audit event; a corrected document is a new attempt after a re-upload decision. |
| Case and attempt statuses | Case: `PENDING`, `PROCESSING`, `AUTO_VERIFIED`, `REVIEW_REQUIRED`, `APPROVED`, `REJECTED`, `REUPLOAD_PENDING`. Attempt: `PROCESSING`, `AUTO_VERIFIED`, `REVIEW_REQUIRED`, `APPROVED`, `REJECTED`, `REUPLOAD_REQUESTED`. | C uses the same values in API types/badges. Poll only while `PROCESSING`; stop at review or other terminal states. |
| Automatic comparison | Aadhaar requires name, date of birth, and gender. PAN requires name and date of birth. Identifiers and Aadhaar address remain extracted/stored for reviewer context but are not automatically compared. Missing required values produce `REVIEW_REQUIRED`; no new score field is added. | C shows returned comparisons and review state; do not imply an address or ID-number match. |
| Upload limits | Accept JPEG, PNG, and PDF; maximum object size is 10 MiB and maximum PDF length is 3 pages. The API checks actual S3 `HeadObject` size/type before queueing; the worker independently caps reads and rejects oversized PDFs. | C rejects oversize files before PUT and displays the 10 MiB/3-page limits. B keeps server-side S3 metadata validation; client-supplied `file_size_bytes` is informational only. |
| Cognito frontend flow | Keep Cognito User Pools. Backend `/auth/register` and `/auth/confirm` own registration because confirmation creates the database customer row. Amplify Auth owns customer/reviewer sign-in, token storage/refresh, and sign-out using the corresponding pool/client and SRP flow. Use one login page with an explicit customer/reviewer selector; reviewer self-registration stays disabled. The existing customer pool has the requested custom attributes; `gender` is the standard Cognito attribute. | B confirmed the attributes are configured. A live read on 2026-10-29 found SRP enabled for both clients; customer `USER_PASSWORD_AUTH` is enabled and reviewer `USER_PASSWORD_AUTH` is absent, which is compatible with Amplify SRP. Backend registration now writes standard `gender` and reads it back. C's registration/confirmation pages call the backend APIs; sign-in/session stays in Amplify. |
| API authorization boundary | Cognito remains the identity provider; FastAPI validates Cognito access-token signature, issuer, expiry, token use, and the selected customer/reviewer pool's app-client ID on protected routes. API Gateway remains a REST proxy without a second authorizer. Registration and confirmation are public; customer and reviewer routes enforce their respective FastAPI dependencies. | A reviewed and fixed the access-token/ID-token mismatch. B's duplicate `/auth/login`, `/auth/refresh`, and `/auth/logout` endpoints are removed from source because Amplify owns those sessions. C attaches the Cognito access token to protected calls. No custom JWT issuer is introduced. |
| Notifications | No customer SNS topic. The worker sends generic SMS directly to the customer's phone via SNS plus email via SES after committed `AUTO_VERIFIED`. B sends reviewer-decision notifications to the customer: approval email; rejection email plus generic SMS; re-upload decision email. Do not notify on ordinary document submission. Messages contain no document values; delivery is best-effort, not exactly-once. | Backend SNS permission is region-scoped for direct-phone delivery; no topic ARN is used for customer SMS. Keep the foundation alarm SNS topic for operations only. B's account SMS spend limit remains to be checked before enabling customer SMS. |
| Static frontend routes | Keep S3 + CloudFront static hosting. Use browser-side route checks and a static reviewer case-detail page that reads `caseId` from the query string. The API remains the authorization boundary. | C avoids Next middleware and runtime-generated dynamic case paths. CloudFront remains disabled until AWS account verification is complete. |
